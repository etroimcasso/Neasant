# The 6502 CPU core

The 6502 is the NES's CPU — the processor inside the 2A03 that runs the game's own code. This is
its instruction-set core: a cycle-stepped interpreter running over an abstract bus, so it executes
the same way on a flat test memory as on a bus a machine supplies.

The core is the CPU and only the CPU: it reads and writes a 16-bit address space the host
supplies. The APU, the DMA units and the controller ports the 2A03 also holds belong to a machine,
built over this core and its RDY line.

All 256 opcodes run: the 151 official ones, the 105 unofficial ones with the unstable seven among
them, and the twelve JAM opcodes as a halted CPU. The reset, NMI, IRQ and BRK sequences run cycle
by cycle, and so does the RDY halt a DMA unit uses. Every cycle is one bus access with a named
kind. The status table in the [README](../README.md) is the component's status row.

## The bus

The core talks to memory through any type that satisfies the `CpuBus` concept — an 8-bit read and
an 8-bit write, each told what the access is for:

```cpp
template <typename B>
concept CpuBus = requires(B bus, std::uint16_t address, std::uint8_t value,
                          CycleKind kind) {
  { bus.read(address, kind) } -> std::same_as<std::uint8_t>;
  bus.write(address, value, kind);
};
```

The address is 16 bits (64 KiB) and the data 8. The 6502 drives the bus on every cycle, so every
cycle the core runs is exactly one of those two calls, made once, and a count of bus calls is a
count of cycles (64doc, "6510 features"; NESdev wiki, "CPU pinout"). A flat array is the simplest
conforming bus:

```cpp
#include "nescore/cpu/cpu6502.h"

#include <array>
#include <cstdint>

struct FlatRam {
  std::array<std::uint8_t, 65536> bytes{};

  std::uint8_t read(std::uint16_t address, nescore::CycleKind) const { return bytes[address]; }
  void write(std::uint16_t address, std::uint8_t value, nescore::CycleKind) {
    bytes[address] = value;
  }

  // Loading memory is not the CPU driving the bus, so it takes no cycle kind.
  void poke(std::uint16_t address, std::uint8_t value) { bytes[address] = value; }
};
```

Every later example on this page uses this `FlatRam` and needs no further `#include`.

`CycleKind` names what each access is for, one enumerator per kind of cycle:

| Kind | The access |
|---|---|
| `OpcodeFetch` | the first byte of an instruction |
| `OperandFetch` | an instruction's operand bytes, read at the program counter |
| `DataRead` | the byte an instruction loads, or a byte of a pointer an indirect mode reads |
| `DataWrite` | the byte an instruction stores |
| `DummyRead` | a read whose value is discarded: the second cycle of an implied instruction, the wrong-page read of an indexed access, a branch's fix-up read, the idle reads of the stack instructions, the reads that open a hardware sequence |
| `RmwRead` | the read of a read-modify-write |
| `RmwDummyWrite` | the unmodified value a read-modify-write writes back |
| `RmwWrite` | the modified value |
| `StackPush` | a write to page one at the stack pointer |
| `StackPull` | a read from page one at the stack pointer |
| `VectorRead` | a byte of the reset, NMI or IRQ/BRK vector |
| `Halted` | a read repeated while the RDY line is low |

A bus that treats all memory alike ignores the kind. A bus that maps hardware uses it to tell a
fetch from a load, to price a region, or to let a watch answer a single access. The core issues
every documented access, the discarded ones included: on a flat memory a discarded read changes
nothing, and on a bus whose reads have side effects — the PPU's `$2002`, the controller ports —
issuing them is what makes the core right (64doc, "6510 features"). `DataWrite`, `RmwDummyWrite`,
`RmwWrite` and `StackPush` are writes; every other kind is a read.

## State

The whole CPU is one value, `Cpu6502State`: snapshot it by copying it, restore it by assignment.

```cpp
struct Cpu6502State {
  std::uint16_t pc = 0;  // program counter
  std::uint8_t s = 0;    // stack pointer, an offset into page one
  std::uint8_t a = 0;    // accumulator
  std::uint8_t x = 0;    // X index register
  std::uint8_t y = 0;    // Y index register
  std::uint8_t p = 0;    // processor status

  // How far into an instruction the core is. These carry no architectural meaning;
  // they are the progress a running instruction has made, held as values so a
  // snapshot taken mid-instruction restores to the same cycle.
  std::uint8_t ir = 0;       // the opcode being executed
  std::uint8_t tcu = 0;      // cycle index within it; 0 means the next cycle fetches
  std::uint16_t ea = 0;      // effective-address latch
  std::uint8_t ptr = 0;      // pointer latch
  std::uint8_t data = 0;     // data latch
  bool pageCross = false;    // an index addition carried past a page

  // The input lines and what the core has latched from them.
  bool nmiLine = false;     // the NMI line's level, true while asserted
  bool nmiPending = false;  // latched by the NMI line becoming asserted; cleared when taken
  bool irqLine = false;     // the IRQ line's level, true while asserted
  bool rdyLine = true;      // the RDY line; false halts the core on its next read
  bool rdyHeld = false;     // RDY has held the cycle under way; cleared when a cycle completes
  // The sequence the last interrupt poll asked for, taken at the next boundary.
  CpuSequence polled = CpuSequence::None;
  // The hardware sequence in progress, or pending at a boundary.
  CpuSequence servicing = CpuSequence::None;
  bool jammed = false;  // halted by a JAM opcode until reset

  [[nodiscard]] bool operator==(const Cpu6502State&) const noexcept = default;
};
```

The fields down to `p` are the architectural registers a program sees. `ir` through `pageCross`
are how far into an instruction the core is, so a copy taken part-way through an instruction is a
complete snapshot and restoring it resumes on the same cycle. `nmiLine` through `rdyHeld` are the
input lines and what the core has latched from them; `polled` and `servicing` carry the interrupt
machinery (see [Interrupts as state](#interrupts-as-state)); `jammed` is the halt a JAM opcode
brings. The struct holds the whole of the execution state. `p` is a plain byte: the core reads and
writes only N, V, D, I, Z and C in it and carries bits 4 and 5 as found, so a byte a host restores
round-trips (NESdev wiki, "Status flags", Flags).

| Mask | Bit | Flag |
|---|---|---|
| `kCpuFlagN` | `0x80` | negative: bit 7 of a result |
| `kCpuFlagV` | `0x40` | signed overflow |
| `kCpuFlagU` | `0x20` | no flag behind it; a push writes it as 1 |
| `kCpuFlagB` | `0x10` | no flag behind it; BRK and PHP push it as 1, NMI and IRQ as 0 |
| `kCpuFlagD` | `0x08` | decimal: held, pushed and pulled, and never honored by ADC or SBC |
| `kCpuFlagI` | `0x04` | interrupt disable |
| `kCpuFlagZ` | `0x02` | zero |
| `kCpuFlagC` | `0x01` | carry |

(NESdev wiki, "Status flags", Flags and The B flag; NESdev wiki, "CPU": the 2A03 has no decimal
mode.)

```cpp
enum class CpuSequence : std::uint8_t { None, Reset, Nmi, Irq };
```

A hardware sequence has no opcode, so the state names which one is running in a `CpuSequence`;
BRK runs the same cycles as an instruction and is not one of these.

## Running instructions

Construct the core from a starting state and step it. `stepInstruction()` runs to the next
instruction boundary and returns how many cycles that took:

```cpp
FlatRam ram;
ram.poke(0x0200, 0xA9);  // LDA #$2A
ram.poke(0x0201, 0x2A);

nescore::Cpu6502 cpu(nescore::Cpu6502State{.pc = 0x0200, .s = 0xFD});
const std::uint32_t cycles = cpu.stepInstruction(ram);

// cpu.state().a  == 0x2A
// cpu.state().pc == 0x0202
// cycles         == 2
```

The full surface:

```cpp
class Cpu6502 {
 public:
  Cpu6502() = default;
  explicit Cpu6502(Cpu6502State state);

  const Cpu6502State& state() const noexcept;   // the current state, by reference
  void restore(Cpu6502State state) noexcept;    // replace it whole

  template <CpuBus B>
  void stepCycle(B& bus);                        // one cycle: one bus access

  template <CpuBus B>
  std::uint32_t stepInstruction(B& bus);         // to the next boundary; the cycles it took

  bool atInstructionBoundary() const noexcept;   // between instructions?

  void reset() noexcept;                         // make the reset sequence pending

  void setNmiLine(bool asserted) noexcept;       // the NMI pin
  void setIrqLine(bool asserted) noexcept;       // the IRQ pin
  void setRdyLine(bool asserted) noexcept;       // the RDY pin
};

constexpr Cpu6502State powerOn() noexcept;       // the power-on state, reset pending
```

Time is external: the caller decides how much to run by counting the cycles returned against
whatever budget it keeps. The core holds no clock, starts no thread and allocates nothing. A
default-constructed core holds a default state and fetches from `$0000` when stepped; a host that
wants a power-on builds from `powerOn()`.

### One cycle at a time

`stepCycle()` runs one cycle, which is one bus access. A machine that interleaves with the CPU
part-way through an instruction — a DMA unit taking the bus, an interrupt line changing at an
exact cycle, a PPU advancing three dots per CPU cycle — drives the core this way:

```cpp
FlatRam ram;
ram.poke(0x0200, 0xAD);  // LDA $1234
ram.poke(0x0201, 0x34);
ram.poke(0x0202, 0x12);
ram.poke(0x1234, 0x7F);

nescore::Cpu6502 cpu(nescore::Cpu6502State{.pc = 0x0200, .s = 0xFD});
cpu.stepCycle(ram);  // the opcode fetch
cpu.stepCycle(ram);  // the low byte of the address
cpu.stepCycle(ram);  // the high byte
// cpu.atInstructionBoundary() == false: the instruction is three cycles in
// cpu.state().ea              == 0x1234
// cpu.state().tcu             == 3
cpu.stepCycle(ram);  // the read at $1234, and the load
// cpu.atInstructionBoundary() == true
// cpu.state().a               == 0x7F
```

`atInstructionBoundary()` reports whether the core sits between instructions. `stepInstruction()`
called part-way through an instruction finishes it rather than starting another, so the two calls
mix freely. Every one of the 256 opcodes runs a cycle at a time; the core runs no opcode whole.

Two things end `stepInstruction()` early, returning the count so far: a cycle that leaves the RDY
line low, and a cycle that jams the core. With either already so on entry it steps one cycle and
returns 1, since no boundary is reachable (see [The RDY line](#the-rdy-line) and
[A jammed core](#a-jammed-core)).

### Snapshot and restore

`state()` answers the value by reference and `restore()` replaces it; both are legal at any cycle:

```cpp
FlatRam ram;
ram.poke(0x0200, 0xAD);  // LDA $1234
ram.poke(0x0201, 0x34);
ram.poke(0x0202, 0x12);
ram.poke(0x1234, 0x7F);

nescore::Cpu6502 cpu(nescore::Cpu6502State{.pc = 0x0200, .s = 0xFD});
cpu.stepCycle(ram);
cpu.stepCycle(ram);
const nescore::Cpu6502State midway = cpu.state();  // two cycles into the load

nescore::Cpu6502 other;
other.restore(midway);
const std::uint32_t rest = other.stepInstruction(ram);
// rest             == 2: the two cycles the instruction had left
// other.state().a  == 0x7F
// other.state()    == the state `cpu` reaches after two more cycles
```

The interpreter is a function of the state and the bus: two cores restored from one snapshot and
driven by one bus end on equal states, which is what `operator==` is for.

### Power-on and reset

Power-on and reset are sequences the core steps, not values it is handed. `powerOn()` answers the
state the chip holds at power-on with the reset sequence pending: A, X and Y zero, S `$00` before
the sequence's three decrements take it to `$FD`, I set and every other flag clear, and the
program counter `$0000` (NESdev wiki, "CPU power up state", CPU).

```cpp
FlatRam ram;
ram.poke(0xFFFC, 0x00);  // the reset vector: $8000
ram.poke(0xFFFD, 0x80);

nescore::Cpu6502 cpu(nescore::powerOn());
const std::uint32_t cycles = cpu.stepInstruction(ram);
// cycles         == 7: the reset sequence
// cpu.state().pc == 0x8000
// cpu.state().s  == 0xFD
// cpu.state().p  == nescore::kCpuFlagI
```

The seven cycles pass through the bus like any others: two discarded reads at the program counter,
three discarded reads at `$0100 + S` with S stepping down each time, then the two vector bytes as
`VectorRead`. A reset runs the interrupt sequence with its writes suppressed, so memory is
untouched (NESdev wiki, "CPU interrupts", IRQ and NMI tick-by-tick execution; NESdev wiki, "CPU
power up state", References).

`reset()` makes the same sequence pending on a running core. The next cycle begins it, an
instruction in progress is abandoned, and a jammed core is released. A, X, Y and every flag but I
keep their values; S loses three and I is set (NESdev wiki, "CPU power up state", CPU; 64doc,
"6510 features").

```cpp
cpu.restore(nescore::Cpu6502State{.pc = 0x4000, .s = 0x80, .a = 0x11, .x = 0x22,
                                  .p = nescore::kCpuFlagN | nescore::kCpuFlagC});
cpu.reset();
cpu.stepInstruction(ram);  // the same seven cycles
// cpu.state().pc == 0x8000
// cpu.state().s  == 0x7D: three lower
// cpu.state().a  == 0x11 and .x == 0x22: kept
// cpu.state().p  == nescore::kCpuFlagN | nescore::kCpuFlagC | nescore::kCpuFlagI
```

`reset()` leaves the lines and the latched NMI as they stand.

### The interrupt lines

`setNmiLine()`, `setIrqLine()` and `setRdyLine()` are the pins, driven by the machine around the
core; `asserted` is true while the active-low pin is held low. NMI is edge-sensitive: the line
becoming asserted latches `nmiPending`, which stays set until the request is taken, so holding the
line asserted asks for nothing more and a fresh edge asks again. IRQ is level-sensitive: the core
samples the level, so a source holds it until acknowledged (NESdev wiki, "CPU interrupts",
Detailed interrupt behavior). RDY low halts the core on its next read cycle (NESdev wiki, "DMA",
Behavior).

```cpp
cpu.setNmiLine(true);   // an edge: cpu.state().nmiPending is now set
cpu.setIrqLine(true);   // a level: cpu.state().irqLine follows the line
cpu.setRdyLine(false);  // the next read cycle is held
```

What the core does with each is under [Interrupts and halts](#interrupts-and-halts).

### The instruction table

One table spells the instruction set: for each of the 256 opcodes, its mnemonic, its addressing
mode, its access class (what the instruction does with the bus once its address is known) and
whether it is unofficial or unstable. The cycle sequences select on the mode and the class, and
cycle counts fall out of the sequences, never from a formula. `opcodeAt(code)` answers the row and
`mnemonicName()` the upper-case spelling.

```cpp
enum class Mnemonic : std::uint8_t {
  Adc, Alr, Anc, And, Ane, Arr, Asl, Bcc, Bcs, Beq, Bit, Bmi, Bne, Bpl, Brk, Bvc, Bvs, Clc,
  Cld, Cli, Clv, Cmp, Cpx, Cpy, Dcp, Dec, Dex, Dey, Eor, Inc, Inx, Iny, Isc, Jam, Jmp, Jsr,
  Las, Lax, Lda, Ldx, Ldy, Lsr, Lxa, Nop, Ora, Pha, Php, Pla, Plp, Rla, Rol, Ror, Rra, Rti,
  Rts, Sax, Sbc, Sbx, Sec, Sed, Sei, Sha, Shx, Shy, Slo, Sre, Sta, Stx, Sty, Tas, Tax, Tay,
  Tsx, Txa, Txs, Tya,
};

enum class AddressingMode : std::uint8_t {
  Implied,
  Accumulator,
  Immediate,
  ZeroPage,
  ZeroPageX,
  ZeroPageY,
  Absolute,
  AbsoluteX,
  AbsoluteY,
  IndexedIndirect,  // (zp,X)
  IndirectIndexed,  // (zp),Y
  Relative,
  Indirect,  // JMP (abs)
};

enum class AccessClass : std::uint8_t {
  Implied,              // registers only; the accumulator shifts included
  Read,                 // loads an operand
  Write,                // stores a value
  ReadModifyWrite,      // reads, writes the value back, writes the result
  Branch,               // a relative branch
  Jump,                 // JMP
  Call,                 // JSR
  Return,               // RTS
  ReturnFromInterrupt,  // RTI
  Push,                 // PHA, PHP
  Pull,                 // PLA, PLP
  Break,                // BRK
  Jam,                  // halts the core until reset
};

struct Opcode {
  Mnemonic mnemonic;
  AddressingMode mode;
  AccessClass access;
  bool unofficial = false;  // outside the documented instruction set
  bool unstable = false;    // the result depends on analog behavior of the chip
};
```

```cpp
const nescore::Opcode& lda = nescore::opcodeAt(0xA9);
// lda.mnemonic == nescore::Mnemonic::Lda
// lda.mode     == nescore::AddressingMode::Immediate
// lda.access   == nescore::AccessClass::Read
// lda.unofficial == false

const nescore::Opcode& ane = nescore::opcodeAt(0x8B);
// ane.mnemonic == nescore::Mnemonic::Ane, ane.unofficial and ane.unstable both true

// nescore::mnemonicName(lda.mnemonic) == "LDA"
```

The unofficial names follow 64doc's matrix, except `ISC`, `ALR` and `TAS`, which follow the NESdev
wiki's. The other spellings in use — `ISB`, `ASR`, `SHS`, `XAA`, `AXS`, `AHX`, `STP`, and
`LAX #imm` for `LXA` — are listed here so a reader working from another document finds the row
(64doc, "6510 Instructions by Addressing Modes"; NESdev wiki, "CPU unofficial opcodes").
`kUnofficial` and `kUnstable` are the spellings the table's rows use for the two flags.

## The cycle bar

Cycle counts match the documented totals (64doc, "6510 Instruction Timing"; NESdev wiki, "CPU
addressing modes"). On the 6502 three rules decide the variable ones: an indexed *read* costs one
cycle more when the index addition carries into the next page; an indexed *store* or
*read-modify-write* always pays that cycle; a branch costs two cycles when not taken, three when
taken, and four when the target is in another page. Every other count is fixed by the mode.

A count is never a formula the core evaluates; it is how many cycles the instruction ran. The bar
is the placement of each access within the instruction as well as the total: which cycle drives
which address, which value crosses the bus, and which reads are discarded — every one of them a
real read on the bus.

## Zero page addressing

`zp`, `zp,X` and `zp,Y` name an address in page zero with one operand byte. The indexed forms add X
or Y to it, and the sum stays in page zero (64doc, "Zero page addressing" and "Zero page indexed
addressing").

```cpp
FlatRam ram;
ram.poke(0x0200, 0xB5);  // LDA $F0,X
ram.poke(0x0201, 0xF0);
ram.poke(0x0010, 0x7F);

nescore::Cpu6502 cpu(nescore::Cpu6502State{.pc = 0x0200, .s = 0xFD, .x = 0x20});
const std::uint32_t cycles = cpu.stepInstruction(ram);
// cycles        == 4
// cpu.state().a == 0x7F: $F0 + $20 wrapped to $10 inside page zero
// the third cycle read $00F0 and discarded it
```

### Where the cycles go

- The opcode fetch.
- The operand byte.
- For an indexed form, one cycle that reads the unindexed address and discards it while the index
  is added.
- The data access.

A read takes 3 cycles (4 indexed), a write 3 (4), and a read-modify-write 5 (6), the extra two per
[Read-modify-write](#read-modify-write).

## Absolute addressing

`abs`, `abs,X` and `abs,Y` name any address with two operand bytes, low then high; the indexed
forms add an index to it (64doc, "Absolute addressing" and "Absolute indexed addressing"). The
index is added to the low byte first. When that carries, the core spends a cycle reading the
address with the high byte not yet fixed — one page below where it is going — and discards it,
then reads the right address. A store or a read-modify-write makes that read whether or not the
page changed, at the address it is about to write (64doc, "6510 features").

```cpp
FlatRam ram;
ram.poke(0x0200, 0xB9);  // LDA $12F0,Y
ram.poke(0x0201, 0xF0);
ram.poke(0x0202, 0x12);
ram.poke(0x1310, 0x7F);

nescore::Cpu6502 cpu(nescore::Cpu6502State{.pc = 0x0200, .s = 0xFD, .y = 0x20});
const std::uint32_t cycles = cpu.stepInstruction(ram);
// cycles        == 5: four, plus the page crossed
// cpu.state().a == 0x7F
// the fourth cycle read $1210, a page low, and discarded it; the fifth read $1310
```

A store through the same mode reads its address before it writes it:

```cpp
FlatRam store;
store.poke(0x0200, 0x9D);  // STA $12F0,X
store.poke(0x0201, 0xF0);
store.poke(0x0202, 0x12);

nescore::Cpu6502 sta(nescore::Cpu6502State{.pc = 0x0200, .s = 0xFD, .a = 0x5A, .x = 0x05});
const std::uint32_t storeCycles = sta.stepInstruction(store);
// storeCycles         == 5, with no page crossed
// store.bytes[0x12F5] == 0x5A
// the fourth cycle read $12F5 and discarded it before the fifth wrote it
```

### Where the cycles go

- The opcode fetch.
- The low byte.
- The high byte, with the index added to the low byte.
- For an indexed read across a page, for every indexed store and for every indexed
  read-modify-write, one cycle reading the address as it stands and discarding it.
- The data access.

A read takes 4 cycles (indexed 4, or 5 across a page), a write 4 (indexed 5), and a
read-modify-write 6 (indexed 7). `JMP abs` takes 3 and is under [The jumps](#the-jumps).

## Indirect addressing

Two modes reach memory through a pointer in page zero. `(zp,X)` adds X to the operand byte and
reads a 16-bit pointer there; `(zp),Y` reads the pointer at the operand byte and adds Y to it
(64doc, "Indexed indirect addressing" and "Indirect indexed addressing"). `(zp),Y` pays the
page-cross cycle on the same terms as `abs,Y`; `(zp,X)` never does, since its index is added
before the pointer is read.

```cpp
FlatRam ram;
ram.poke(0x0200, 0xB1);  // LDA ($FF),Y
ram.poke(0x0201, 0xFF);
ram.poke(0x00FF, 0x34);  // the pointer's low byte
ram.poke(0x0000, 0x12);  // its high byte, read from $00, not $0100
ram.poke(0x1234, 0x7F);

nescore::Cpu6502 cpu(nescore::Cpu6502State{.pc = 0x0200, .s = 0xFD});
const std::uint32_t cycles = cpu.stepInstruction(ram);
// cycles        == 5
// cpu.state().a == 0x7F
```

### Where the cycles go

For `(zp,X)`:

- The opcode fetch.
- The operand byte.
- One cycle reading the unindexed address and discarding it while X is added.
- The pointer's low byte.
- Its high byte.
- The data access.

That is 6 cycles for a read or a store and 8 for a read-modify-write.

For `(zp),Y`:

- The opcode fetch.
- The operand byte.
- The pointer's low byte.
- Its high byte, with Y added to the low byte.
- The page-fix read, when a read crosses a page, and always for a store or a read-modify-write.
- The data access.

That is 5 cycles for a read (6 across a page), 6 for a store and 8 for a read-modify-write. The
pointer bytes are `DataRead` cycles in both modes.

### Where a pointer wraps

Both of a pointer's bytes are in page zero: a pointer whose low byte is at `$FF` has its high byte
at `$00`, in both modes. The X addition of `(zp,X)` wraps inside page zero too (64doc, "6510
features"). The `JMP (abs)` pointer has its own rule under [The jumps](#the-jumps).

## Read-modify-write

`ASL`, `LSR`, `ROL`, `ROR`, `INC` and `DEC` read their operand, write the unmodified value back to
the same address while the operation runs, then write the result — so a read-modify-write writes
its address twice (64doc, "6510 features"). On a flat memory the first write is invisible; on a
bus whose writes have side effects, both land. The three cycles carry `RmwRead`, `RmwDummyWrite`
and `RmwWrite`.

```cpp
FlatRam ram;
ram.poke(0x0200, 0xE6);  // INC $10
ram.poke(0x0201, 0x10);
ram.poke(0x0010, 0x7F);

nescore::Cpu6502 cpu(nescore::Cpu6502State{.pc = 0x0200, .s = 0xFD});
const std::uint32_t cycles = cpu.stepInstruction(ram);
// cycles          == 5
// ram.bytes[0x10] == 0x80, and the negative flag is set
// the third cycle read $7F from $0010, the fourth wrote $7F back, the fifth wrote $80
```

The counts for the three classes, by mode:

| Mode | Read | Write | Read-modify-write |
|---|---|---|---|
| `#imm` | 2 | — | — |
| `zp` | 3 | 3 | 5 |
| `zp,X` / `zp,Y` | 4 | 4 | 6 |
| `abs` | 4 | 4 | 6 |
| `abs,X` / `abs,Y` | 4, or 5 across a page | 5 | 7 |
| `(zp,X)` | 6 | 6 | 8 |
| `(zp),Y` | 5, or 6 across a page | 6 | 8 |

(64doc, "6510 Instruction Timing".) The accumulator forms `ASL A`, `LSR A`, `ROL A` and `ROR A` are
two-cycle implied instructions, like the transfers, the index steps, the flag instructions and
`NOP`: the opcode fetch, then a read of the byte after it, discarded, with the program counter
staying where it is (64doc, "Accumulator or implied addressing").

## Control flow

The control-flow instructions are the eight conditional branches, the two jumps, `JSR`, `RTS`,
`RTI`, and the four stack instructions `PHA`, `PHP`, `PLA` and `PLP`. `BRK` is under
[Interrupts and halts](#interrupts-and-halts).

### The branches

A branch reads a signed 8-bit displacement and adds it to the address of the next instruction, so
`$FE` branches to itself and `$00` falls through.

| | Taken when | | Taken when |
|---|---|---|---|
| `BPL` / `BMI` | N clear / set | `BVC` / `BVS` | V clear / set |
| `BCC` / `BCS` | C clear / set | `BNE` / `BEQ` | Z clear / set |

(NESdev wiki, "Instruction reference", BCC through BVS.) The opcode fetch and the displacement take
two cycles, the whole instruction when the branch is not taken. A taken branch adds one cycle,
reading the byte after the displacement and discarding it while the low byte of the target is
formed. A target in another page adds one more, reading the target's low byte in the old page and
discarding it before the high byte is fixed (64doc, "Relative addressing"; 64doc, "6510
features").

```cpp
FlatRam ram;
ram.poke(0x02F0, 0xD0);  // BNE +$20, which lands in the next page
ram.poke(0x02F1, 0x20);

nescore::Cpu6502 cpu(nescore::Cpu6502State{.pc = 0x02F0, .s = 0xFD});
const std::uint32_t cycles = cpu.stepInstruction(ram);
// cycles         == 4: two, one for the branch taken, one for the page crossed
// cpu.state().pc == 0x0312
// the third cycle read $02F2 and the fourth read $0212, both discarded
```

A branch's interrupt polling has its own rule under
[When a request is taken](#when-a-request-is-taken).

### The jumps

The two jumps load the program counter directly or through a pointer:

| | Cycles | Destination |
|---|---|---|
| `JMP abs` | 3 | the operand |
| `JMP (abs)` | 5 | the word at the operand's address |

(64doc, "Absolute addressing", JMP; 64doc, "Absolute indirect addressing (JMP)".) The indirect
form reads the pointer's second byte from the same page as its first: `JMP ($12FF)` reads `$12FF`
and `$1200`, not `$1300` (64doc, "6510 features").

```cpp
FlatRam ram;
ram.poke(0x0200, 0x6C);  // JMP ($12FF)
ram.poke(0x0201, 0xFF);
ram.poke(0x0202, 0x12);
ram.poke(0x12FF, 0x34);  // the pointer's low byte
ram.poke(0x1200, 0x56);  // its high byte: read from $1200, not $1300
ram.poke(0x1300, 0x99);

nescore::Cpu6502 cpu(nescore::Cpu6502State{.pc = 0x0200, .s = 0xFD});
const std::uint32_t cycles = cpu.stepInstruction(ram);
// cycles         == 5
// cpu.state().pc == 0x5634
```

### The calls and returns

`JSR` pushes the address of its own last byte — one short of the next instruction — and `RTS` adds
one back, so control resumes after the call. `RTI` pulls the status first, bits 4 and 5 excepted,
then the address, and uses the address as it stands (64doc, "Instructions accessing the stack",
JSR, RTS and RTI; NESdev wiki, "Instruction reference", RTI).

| | Cycles | After the opcode fetch |
|---|---|---|
| `JSR abs` | 6 | the destination's low byte; a discarded read at the stack pointer; the return address pushed high byte then low; the destination's high byte |
| `RTS` | 6 | a discarded read at the program counter; a discarded read at the stack pointer; the address pulled low byte then high; a discarded read at that address, then the step past it |
| `RTI` | 6 | a discarded read at the program counter; a discarded read at the stack pointer; the status; the address, low byte then high |

(64doc, "Instructions accessing the stack".) `JSR` writes its return address before it has
finished reading its own operand: the two stack writes sit between the two operand fetches.

```cpp
FlatRam ram;
ram.poke(0x1000, 0x20);  // JSR $2000
ram.poke(0x1001, 0x00);
ram.poke(0x1002, 0x20);
ram.poke(0x2000, 0x60);  // RTS

nescore::Cpu6502 cpu(nescore::Cpu6502State{.pc = 0x1000, .s = 0xFD});
cpu.stepInstruction(ram);
// cpu.state().pc == 0x2000; $01FD holds $10 and $01FC holds $02: the address $1002
cpu.stepInstruction(ram);
// cpu.state().pc == 0x1003, the instruction after the call, and S is back at $FD
```

### The stack instructions

The stack lives in page one and the pointer wraps inside it: a push at `$0100` steps the pointer
to `$FF`. A push writes at the pointer and then steps it down; a pull steps it up and then reads.
`PHA` and `PHP` take three cycles — the opcode fetch, a discarded read of the next byte, the push.
`PLA` and `PLP` take four — the same two, a discarded read at the stack pointer, the pull. `PHP`
pushes bits 5 and 4 set; `PLA` sets N and Z from what it pulled; `PLP` loads every flag and leaves
bits 4 and 5 as they were (64doc, "Instructions accessing the stack", PHA, PHP, PLA, PLP; NESdev
wiki, "Status flags", The B flag; NESdev wiki, "Instruction reference", PLP).

```cpp
FlatRam ram;
ram.poke(0x0200, 0x08);  // PHP
ram.poke(0x0201, 0x28);  // PLP

nescore::Cpu6502 cpu(nescore::Cpu6502State{.pc = 0x0200, .s = 0xFC, .p = 0x00});
cpu.stepInstruction(ram);  // PHP: 3 cycles
// ram.bytes[0x01FC] == 0x30: bits 5 and 4 pushed set, the flags all clear
// cpu.state().s     == 0xFB
ram.poke(0x01FC, 0xFF);    // replace the pushed byte with every bit set
cpu.stepInstruction(ram);  // PLP: 4 cycles
// cpu.state().p == 0xCF: every flag loaded, bits 5 and 4 left as they were
// cpu.state().s == 0xFC
```

## Interrupts and halts

Four things start the seven-cycle sequence: the `BRK` instruction, the two request lines and the
reset line. They differ in the vector, in the first two cycles, in whether the stack is written,
and in one bit of the pushed status.

### The sequence

Cycle by cycle, the four forms run side by side:

| Cycle | Reset | NMI and IRQ | BRK |
|---|---|---|---|
| 1 | reads the program counter, discards | the same | the opcode fetch; PC + 1 |
| 2 | reads the program counter, discards | the same | reads the byte after the opcode, discards; PC + 1 |
| 3 | reads `$0100 + S`, discards; S − 1 | pushes PCH | pushes PCH |
| 4 | reads `$0100 + S`, discards; S − 1 | pushes PCL | pushes PCL |
| 5 | reads `$0100 + S`, discards; S − 1 | pushes P with bit 5 set and bit 4 clear | pushes P with bits 5 and 4 set |
| 6 | reads `$FFFC`; I is set | reads `$FFFA` or `$FFFE`; I is set | reads `$FFFE`; I is set |
| 7 | reads `$FFFD`; PC = the vector | reads `$FFFB` or `$FFFF`; the same | reads `$FFFF`; the same |

(NESdev wiki, "CPU interrupts", IRQ and NMI tick-by-tick execution; 64doc, "Instructions accessing
the stack", BRK; NESdev wiki, "CPU power up state", References; NESdev wiki, "Status flags", The B
flag.) A hardware sequence reads the program counter twice without advancing it, so the address
saved is the interrupted instruction's own and `RTI` resumes there; `BRK` advances past its two
bytes, so a handler returns past both. The two vector cycles carry `VectorRead`, and they are the
only cycles that do. A reset's three stack cycles are reads, so S ends three lower with memory
untouched.

### The vectors

Each source reads its own vector and marks the status it pushes:

| Source | Vector | Bit 4 of the pushed status |
|---|---|---|
| NMI | `$FFFA` | 0 |
| Reset | `$FFFC` | nothing is pushed |
| IRQ | `$FFFE` | 0 |
| `BRK` | `$FFFE` | 1 |

(NESdev wiki, "CPU interrupts"; NESdev wiki, "Status flags", The B flag.) `BRK` and IRQ share a
vector; bit 4 of the byte on the stack tells a handler which it was.

### When a request is taken

The core decides when a request is answered by these rules (NESdev wiki, "CPU interrupts",
Detailed interrupt behavior; 64doc, "Interrupts"; MCS6500 hardware manual 1.4.1.2.9 and
1.4.1.2.10):

- The core polls the lines before every cycle of an instruction, and the poll that decides whether
  a sequence follows the instruction is the one before its last cycle — which sees the lines as
  they stood at the end of the second-to-last cycle. A line asserted after that waits one
  instruction more.
- NMI is taken whatever I says; the latched edge is cleared as the sequence begins. IRQ is taken
  only while I is clear; otherwise the line is simply held, and the request is answered when I
  clears if the source is still asserting it. With both ready, NMI wins.
- The sequences themselves do not poll, and I is set inside them, so at least one instruction of
  the handler runs before another sequence can begin.
- A taken branch does not poll before its third cycle. A branch across a page polls before its
  fourth, and that poll keeps a request the poll before the second cycle found even when the line
  has since dropped (NESdev wiki, "CPU interrupts", Branch instructions and interrupts).

```cpp
FlatRam ram;
ram.poke(0x1000, 0xEA);  // NOP
ram.poke(0xFFFE, 0x00);  // the IRQ vector: $2000
ram.poke(0xFFFF, 0x20);

nescore::Cpu6502 cpu(nescore::Cpu6502State{.pc = 0x1000, .s = 0xFD});
cpu.setIrqLine(true);
const std::uint32_t first = cpu.stepInstruction(ram);
// first          == 2: the NOP runs; its last cycle's poll finds the request
const std::uint32_t second = cpu.stepInstruction(ram);
// second         == 7: the sequence
// cpu.state().pc == 0x2000
// $01FD and $01FC hold $10 and $01: the address of the instruction after the NOP
// $01FB holds $20: the status with bit 5 set and bit 4 clear
// cpu.state().p has nescore::kCpuFlagI set
```

### The one-instruction delay

`CLI`, `SEI` and `PLP` change I on their last cycle, after that cycle's poll, so the change is
first seen by the next instruction's polls. An IRQ pending when `CLI` runs is taken after the
instruction that follows, and an IRQ found by the poll before `SEI`'s last cycle is taken although
`SEI` has set I. `RTI` behaves differently: it pulls P on its fourth cycle and its last poll sees
the pulled I, so a pending IRQ is taken straight after it (NESdev wiki, "CPU interrupts", Delayed
IRQ response after CLI, SEI, and PLP; MCS6500 programming manual, Example 9.3).

```cpp
FlatRam delay;
delay.poke(0x1000, 0x58);  // CLI
delay.poke(0x1001, 0xEA);  // NOP
delay.poke(0xFFFE, 0x00);
delay.poke(0xFFFF, 0x20);

nescore::Cpu6502 masked(
    nescore::Cpu6502State{.pc = 0x1000, .s = 0xFD, .p = nescore::kCpuFlagI, .irqLine = true});
masked.stepInstruction(delay);  // CLI: I clears on its last cycle, after that cycle's poll
masked.stepInstruction(delay);  // the NOP runs
// masked.state().pc == 0x1002
masked.stepInstruction(delay);  // then the sequence
// masked.state().pc == 0x2000
```

### A sequence taken over

The vector is decided as the fifth cycle begins. An NMI latched during the first four cycles of an
IRQ sequence or of a `BRK` takes the sequence over: the status byte is pushed as the sequence in
progress would push it — bit 4 set for a `BRK` — and the remaining two cycles read the NMI vector,
so the IRQ's or the `BRK`'s own handler never runs for that request. An NMI latched after the
status push waits for the handler's first instruction. A reset is never taken over (NESdev wiki,
"CPU interrupts", Interrupt hijacking; MCS6500 programming manual, 9.10).

### The RDY line

A DMA unit takes the bus by pulling RDY low. The core honors the line at its next read cycle: that
cycle's read is issued as `Halted` at the address the real read would use, the state stays where
it is, and every further cycle while the line is low repeats the same read. When the line rises
the read is made for real and the instruction goes on. A write cycle proceeds whatever the line
says, so a unit that drops RDY during an instruction's writes waits for its next read — after a
`BRK`'s or an interrupt's three pushes, or a read-modify-write's two writes (NESdev wiki, "DMA",
Behavior; 64doc, "6510 features"; MCS6500 hardware manual 1.4.1.2.8). `rdyHeld` in the state
records that the cycle under way was held, for the one instruction family that stores differently
afterwards ([The stores through the high byte](#the-stores-through-the-high-byte)).

```cpp
FlatRam ram;
ram.poke(0x0200, 0xEA);  // NOP
ram.poke(0x0201, 0xEA);

nescore::Cpu6502 cpu(nescore::Cpu6502State{.pc = 0x0200, .s = 0xFD});
cpu.stepCycle(ram);  // the opcode fetch
cpu.setRdyLine(false);
cpu.stepCycle(ram);  // a Halted read of $0201: nothing advances
cpu.stepCycle(ram);  // the same read again
// cpu.state().tcu     == 1
// cpu.state().rdyHeld == true
cpu.setRdyLine(true);
const std::uint32_t rest = cpu.stepInstruction(ram);
// rest == 1: the read the core was held on, made for real, ends the NOP
// cpu.atInstructionBoundary() == true
```

`stepInstruction()` returns when a cycle leaves RDY low, with the count so far, since no boundary
is reachable; a bus that drops the line from inside a write — the way a write to `$4014` starts an
OAM DMA — ends the call after that cycle. A line change made from inside a bus call is kept: the
lines and the NMI latch are the one part of the state a held cycle does not put back. The count of
`Halted` reads a transfer causes is the number of cycles it held the CPU. The OAM DMA's 513 or 514
and the DMC DMA's 3 or 4, by the alignment of the halt, are the machine's to produce and its tests'
to count (NESdev wiki, "DMA", Summary, OAM DMA and DMC DMA).

### A jammed core

Twelve opcodes halt the chip. The core runs them as six cycles — the opcode fetch, a read of the
byte after it, then reads of `$FFFF`, `$FFFE`, `$FFFE` and `$FFFF` — and then repeats a discarded
read of `$FFFF` on every cycle until reset. The program counter steps past the byte after the
opcode; the other registers and the flags keep their values; no interrupt is taken; and
`stepInstruction()` returns 1 per call (No More Secrets, "JAM (KIL, HLT, CIM, CRP)"; NESdev wiki,
"CPU unofficial opcodes"; 64doc, "Different CPU types"; Visual6502, opcode $02, for the two
`$FFFE` reads).

```cpp
FlatRam ram;
ram.poke(0x0200, 0x02);  // JAM
ram.poke(0x0201, 0xEA);
ram.poke(0xFFFC, 0x00);  // the reset vector: $8000
ram.poke(0xFFFD, 0x80);

nescore::Cpu6502 cpu(nescore::Cpu6502State{.pc = 0x0200, .s = 0xFD, .a = 0x11});
const std::uint32_t cycles = cpu.stepInstruction(ram);
// cycles              == 6: the opcode, the byte after it, then $FFFF, $FFFE, $FFFE, $FFFF
// cpu.state().jammed  == true
// cpu.state().pc      == 0x0202
cpu.setNmiLine(true);
const std::uint32_t more = cpu.stepInstruction(ram);
// more == 1: one more discarded read of $FFFF; no interrupt is taken
cpu.reset();
cpu.stepInstruction(ram);
// cpu.state().pc == 0x8000, cpu.state().jammed == false, cpu.state().a == 0x11
```

### Interrupts as state

A hardware sequence has no opcode, so `state().servicing` says which one is running.
`state().polled` is what the last poll asked for, taken at the next boundary, and
`state().nmiPending` is the latched edge. All three are plain values: a state copied part-way
through a sequence restores to the same cycle of the same sequence, and a snapshot taken between
two instructions carries the request the next boundary will take.

## The unofficial opcodes

The 105 opcodes outside the documented set all run, in the families below. The six
read-modify-write combinations run one of the documented read-modify-write operations on the byte
and an accumulator operation on its result, applied on the write-back cycle. The unstable seven
are marked in the table and explained after it. The `Flags` column names the flags the operation
moves; `M` is the operand byte and `H` the high byte of the address the instruction names before
indexing.

| Opcodes | Mnemonic | Operation | Flags |
|---|---|---|---|
| `1A 3A 5A 7A DA FA` | `NOP` | two cycles, nothing | — |
| `80 82 89 C2 E2` | `NOP #imm` | reads the operand, discards it | — |
| `04 44 64` | `NOP zp` | reads the byte, discards it | — |
| `14 34 54 74 D4 F4` | `NOP zp,X` | the same | — |
| `0C` | `NOP abs` | the same | — |
| `1C 3C 5C 7C DC FC` | `NOP abs,X` | the same, with the page-cross cycle | — |
| `EB` | `SBC #imm` | `SBC` | N V Z C |
| `03 07 0F 13 17 1B 1F` | `SLO` | M = `ASL` M; A = A OR M | N Z C |
| `23 27 2F 33 37 3B 3F` | `RLA` | M = `ROL` M; A = A AND M | N Z C |
| `43 47 4F 53 57 5B 5F` | `SRE` | M = `LSR` M; A = A EOR M | N Z C |
| `63 67 6F 73 77 7B 7F` | `RRA` | M = `ROR` M; A = A + M + C, the carry the rotate left | N V Z C |
| `C3 C7 CF D3 D7 DB DF` | `DCP` | M = M − 1; compare A with M | N Z C |
| `E3 E7 EF F3 F7 FB FF` | `ISC` | M = M + 1; A = A − M − (1 − C) | N V Z C |
| `A3 A7 AF B3 B7 BF` | `LAX` | A = X = M | N Z |
| `0B 2B` | `ANC` | A = A AND M; C = bit 7 of A | N Z C |
| `4B` | `ALR` | A = (A AND M) `LSR` 1 | N Z C |
| `6B` | `ARR` | A = (A AND M) `ROR` 1; C = bit 6 of A; V = bit 6 XOR bit 5 | N V Z C |
| `CB` | `SBX` | X = (A AND X) − M, with no borrow in; the flags as a compare sets them | N Z C |
| `BB` | `LAS` | S = S AND M; A = X = S | N Z |
| `8B` | `ANE` *(unstable)* | A = (A OR `$EE`) AND X AND M | N Z |
| `AB` | `LXA` *(unstable)* | A = X = (A OR `$EE`) AND M | N Z |
| `83 87 8F 97` | `SAX` | M = A AND X | — |
| `93 9F` | `SHA` *(unstable)* | M = A AND X AND (H + 1) | — |
| `9E` | `SHX` *(unstable)* | M = X AND (H + 1) | — |
| `9C` | `SHY` *(unstable)* | M = Y AND (H + 1) | — |
| `9B` | `TAS` *(unstable)* | S = A AND X; M = S AND (H + 1) | — |
| `02 12 22 32 42 52 62 72 92 B2 D2 F2` | `JAM` | halts the core; [A jammed core](#a-jammed-core) | — |

(NESdev wiki, "CPU unofficial opcodes"; NESdev wiki, "Programming with unofficial opcodes", RMW
instructions, Combined operations and Unimplemented addressing modes; 64doc, "6510/8502
Undocumented Commands"; No More Secrets, "LAS (LAR)", "LAX #imm" and "'Magic Constant' group".)

The modes of each row are the official rows' modes in the same column of the opcode matrix, and
the cycle counts are those modes' counts. `ARR` is the binary operation only, since the 2A03 has
no decimal mode (NESdev wiki, "CPU"). `ANE` and `LXA` OR a constant into A before their ANDs, and
on the chip that constant varies with the unit, its temperature and the RDY line. The core holds
it at `$EE` — the value 64doc states for `ANE` and the value No More Secrets advises for `LXA` — so
the two instructions are deterministic here, and a program that depends on another value sees a
different result (64doc, "6510/8502 Undocumented Commands"; No More Secrets, "'Magic Constant'
group").

```cpp
FlatRam ram;
ram.poke(0x0200, 0xAB);  // LXA #$FF
ram.poke(0x0201, 0xFF);

nescore::Cpu6502 cpu(nescore::Cpu6502State{.pc = 0x0200, .s = 0xFD, .a = 0x00, .x = 0x55});
cpu.stepInstruction(ram);
// cpu.state().a == 0xEE and cpu.state().x == 0xEE: ($00 | $EE) & $FF
```

### The stores through the high byte

`SHA`, `SHX`, `SHY` and `TAS` store a register value ANDed with the high byte of the address they
name plus one. The mask is latched on the page-fix cycle: the fourth cycle of `abs,Y` and `abs,X`,
the fifth of `(zp),Y`. Two things follow from that cycle. When the index addition carried into the
next page, the register value ANDed with that same high-byte-plus-one also replaces the high byte
of the address, so the write lands in the page the masked value names rather than the page the
addition reached. And when the RDY line held that cycle before it ran, the mask is dropped: the
register value is stored as it is, while the address rule still applies (64doc, "6510/8502
Undocumented Commands"; NESdev wiki, "Programming with unofficial opcodes", Unimplemented
addressing modes; No More Secrets, "'unstable address high byte' group"). `TAS` loads S with A AND
X on the same cycle.

```cpp
FlatRam shx;
shx.poke(0x0200, 0x9E);  // SHX $1200,Y
shx.poke(0x0201, 0x00);
shx.poke(0x0202, 0x12);

nescore::Cpu6502 a(nescore::Cpu6502State{.pc = 0x0200, .s = 0xFD, .x = 0xFF, .y = 0x05});
a.stepInstruction(shx);
// shx.bytes[0x1205] == 0x13: X AND ($12 + 1)

FlatRam across;
across.poke(0x0200, 0x9E);  // SHX $12F0,Y, with Y carrying into the next page
across.poke(0x0201, 0xF0);
across.poke(0x0202, 0x12);

nescore::Cpu6502 b(nescore::Cpu6502State{.pc = 0x0200, .s = 0xFD, .x = 0x03, .y = 0x20});
b.stepInstruction(across);
// across.bytes[0x0310] == 0x03: the value is $03 AND $13, and so is the page it lands in
// across.bytes[0x1310] == 0x00

FlatRam held;
held.poke(0x0200, 0x9E);  // SHX $1200,Y again, with RDY low on its fourth cycle
held.poke(0x0201, 0x00);
held.poke(0x0202, 0x12);

nescore::Cpu6502 c(nescore::Cpu6502State{.pc = 0x0200, .s = 0xFD, .x = 0xFF, .y = 0x05});
c.stepCycle(held);
c.stepCycle(held);
c.stepCycle(held);
c.setRdyLine(false);
c.stepCycle(held);  // the fourth cycle, held
c.setRdyLine(true);
c.stepInstruction(held);
// held.bytes[0x1205] == 0xFF: the mask is gone; X is stored as it is
```

## Testing against the vectors

The core is checked per opcode against the SingleStepTests `65x02` repository's `nes6502` set,
version 1: one file per opcode, ten thousand cases each, every case a state before, a state after,
and one row per cycle — the address, the byte and the direction.

The suite runs a case for exactly as many cycles as it recorded and compares every one of them —
the address driven, the byte that crossed the bus and the direction — then the six registers,
every memory cell the case lists, and that no address outside the case's lists was touched. The
core must finish on an instruction boundary. The twelve JAM files are the exception: their cases
record eleven cycles of a halted CPU, so for them the suite asserts the halt instead of the
boundary and compares the registers other than the program counter, which the set records one
short of where the chip leaves it (the Visual6502 reading under [A jammed core](#a-jammed-core)).

The set is reference data and is not vendored. Point the build at a local checkout:

```
cmake -B build -DNESCORE_NES6502_VECTORS=/path/to/65x02/nes6502/v1
cmake --build build
ctest --test-dir build
```

Without that path the 256 vector cases register and skip, naming the variable; the hand-derived
suites run regardless. Two environment variables adjust the run: `NESCORE_NES6502_CASE_CAP=N` runs
at most `N` cases per file and prints what it truncated, and `NESCORE_REQUIRE_NES6502_VECTORS=1`
turns the skip into a failure, so an environment that means to run the vectors cannot report green
without them.

The hand-derived suites, by executable:

- `cpu_state_test` — the state value, the concept, power-on and reset, the halt and the jam.
- `cpu_modes_test` — every addressing mode and control-flow sequence, cycle by cycle with its
  kinds.
- `cpu_operations_test` — every official operation's result and flags against the programming
  manual's worked examples.
- `cpu_lines_test` — the interrupt timing, the branch rule, the takeover, the halt and the DMA
  cycle counts.
- `cpu_unofficial_test` — every unofficial operation, the high-byte stores with and without a
  hold, and the jam.

Every value they assert is read from a document named under [Sources](#sources).

## Gotchas

- **Every cycle reaches the bus, discarded reads included.** An indexed read across a page reads an
  address one page low before the right one; a store or read-modify-write through an indexed mode
  reads its address before writing it; an implied instruction reads the byte after its opcode; the
  stack instructions read at the stack pointer before pulling. On a bus whose reads have side
  effects, every one of them counts.
- **A read-modify-write writes twice.** The unmodified byte, then the result, to the same address on
  consecutive cycles.
- **`JMP (abs)` does not carry into the next page.** The pointer's high byte is read from the same
  page as its low byte: `JMP ($12FF)` reads `$12FF` and `$1200`.
- **Page-zero pointers wrap in page zero.** `(zp,X)` adds X inside page zero, and both indirect
  modes read a pointer at `$FF` from `$FF` and `$00`.
- **The stack pointer wraps in page one.** A push at `$0100` goes to `$0100` and the pointer becomes
  `$FF`.
- **Bits 4 and 5 of P are not flags.** `PHP` and `BRK` push them set, NMI and IRQ push bit 5 set and
  bit 4 clear, and `PLP` and `RTI` leave them as they were. Compare the whole byte against what the
  chip holds, not against what was pushed.
- **The D flag changes nothing.** `ADC` and `SBC` are binary whatever D says; `SED` and `CLD` move
  the bit and nothing else.

```cpp
FlatRam ram;
ram.poke(0x0200, 0x69);  // ADC #$15
ram.poke(0x0201, 0x15);

nescore::Cpu6502 cpu(
    nescore::Cpu6502State{.pc = 0x0200, .s = 0xFD, .a = 0x27, .p = nescore::kCpuFlagD});
cpu.stepInstruction(ram);
// cpu.state().a == 0x3C: binary, with D set; a 6502 with decimal mode would leave $42
```

- **An interrupt asserted on an instruction's last cycle waits.** The poll that decides is the one
  before the last cycle; `CLI`, `SEI` and `PLP` take effect one instruction late for the same
  reason, and `RTI` takes effect at once.
- **`stepInstruction()` can return early.** A cycle that leaves RDY low or jams the core ends the
  call with the count so far; a caller spending a budget checks `atInstructionBoundary()` rather
  than assuming each call ran one instruction.
- **A default-constructed core is not powered on.** It fetches from `$0000` with every register
  zero; build from `powerOn()` for the chip's power-on state and the seven-cycle reset.
- **`ANE` and `LXA` are deterministic here and not on the chip.** The constant is `$EE`.

## What remains open

What the code does at each point below is fixed and tested; what the chip does is not settled by
the documents the core is built from.

1. **An NMI during a reset.** An NMI edge arriving during a reset sequence stays latched and is
   taken after the first instruction at the reset vector.
2. **When the NMI latch clears.** The core clears it as the sequence begins — at the boundary, or
   at the takeover on the fifth cycle. The NESdev wiki's "NMI" page places the clearing after the
   vector read; its "CPU interrupts" page says the internal signal stays raised until the NMI has
   been handled. An edge arriving during an NMI sequence's last three cycles is therefore latched
   again by the core and taken after the handler's first instruction; neither page fixes whether
   the chip does the same.
3. **The lines during a halt.** A held cycle's poll is discarded with the rest of the cycle, and the
   cycle that runs on release polls the lines as they then stand; the NESdev wiki's "DMA" page says
   only that a halted CPU is not handling interrupts. The suite asserts what both readings agree
   on: a request arriving during a halt is taken after the halted instruction.
4. **The cycle on which I is set inside a sequence.** The NESdev wiki's "CPU interrupts" page gives
   the sixth; the MCS6500 programming manual's Example 9.2 gives the seventh. The sequences do not
   poll, so the difference is unobservable; the core sets I on the sixth.
5. **The DMA units and the regions.** The DMC DMA's timing against the `$4015` write, the get/put
   alignment at power-on, a DMC fetch overlapping an OAM DMA and the DMC's documented bugs belong
   to the APU and the machine over this core, which supplies the halt and nothing else. The PAL
   2A07's address during a halted cycle is a matter for the regions; the core is the NTSC 2A03's.
6. **`ANE`'s and `LXA`'s constant.** On the chip it varies with the unit, its temperature and the
   RDY line: No More Secrets reads `$EF` for `ANE` in an ordinary cycle and `$EE` under RDY, and
   64doc gives `$EE`. The core holds `$EE` for both, whatever the RDY line does.
7. **Where a read-modify-write combination's accumulator half lands.** The NESdev wiki's "CPU
   unofficial opcodes" page has the read-modify-write part complete during the opcode and the ALU
   part during the next opcode's fetch; the core applies both on the write-back cycle. The state
   at every instruction boundary is the same either way; a snapshot taken on the instruction's
   last cycle shows A and the flags already changed.
8. **`ALR` on clone chips.** The NESdev wiki notes it is unreliable on at least one famiclone chip;
   the core is the 2A03.
9. **The jammed CPU's data bus.** No More Secrets has the data and address buses set to all ones.
   The core's bus answers a jammed read from memory as it answers every read, so the value is
   whatever the bus holds at `$FFFF`.

## Where to look

- `include/nescore/cpu/cpu6502.h` — the whole core: `CycleKind`, the `CpuBus` concept,
  `Cpu6502State`, the flag masks, the opcode-table types, `powerOn()`, and `Cpu6502` with its cycle
  engine and every addressing-mode, control-flow and sequence function.
- `src/cpu/cpu6502.cpp` — the 256-row opcode table and its compile-time checks, the mnemonic
  spellings, and the operations: implied, read, read-modify-write, store, and the branch
  conditions.
- `tests/cpu/` — the vector harness and runner, and the five hand-derived suites.
